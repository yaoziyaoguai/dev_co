# 仓库建立与增量维护

**读取时机：** 首次开始持续实施、当前增量要新增目录/资料、移动入口，或现有记录出现归属与更新缺口时。已接入且规则未变时直接沿用；只读讨论、孤立小改不初始化。已有等效项目检查器优先接入，不再建一套并行配置或状态。

章节导航：目录与资料职责 → `建立一次，按变化维护`；机器规则及命令 → `可执行约定`；换增量、分支或旧基线 → `基线来源与换增量`；结合功能验证 → `接到完成出口，避免重复工作`。

## 建立一次，按变化维护

- 新项目按第一版和技术栈选择实际需要的结构。已有项目沿用目录、命令、状态格式和权威资料；约束本次新增及直接受影响的接口/资料，不追溯整理无关存量。
- 在项目已有入口说明关键目录的职责、资料的权威位置、运行与验证方式。普通落位由 agent 决定；只有实质产品、成本、权限或难以撤销的取舍才问用户。没有实际内容就不创建空目录。
- 同一事实只维护一处；README 负责使用，当前记录负责有效目标与接手，契约/架构资料负责各自决定。其他文档引用来源。现有 Spec Kit 或原生任务系统保留原产物，当前记录只作导航。
- 区分长期源码/契约、可复现的测试/样本、当前记录、历史证据和运行数据。运行目录可以包含活跃会话；目录名、体积或文件年龄不能作为自动删除授权。阶段结束时保留有效约束，归档长历史并修复入口，不生成重复总结。

## 更新触发条件

| 变化 | 核对与更新 |
| --- | --- |
| 安装、启动、配置、用户操作 | README/配置示例与相关验证 |
| API、事件、数据结构或文件格式 | 原契约、调用方与相关测试 |
| 模块职责、依赖边界或重要取舍 | 必要的架构说明/决定及代码导航 |
| 目标、范围、验收 | 当前有效表述、受影响的规格/任务、待更新的证据 |
| 新增、移动、删除资料/入口 | 文件归属、适用引用与运行路径 |
| 可交付增量结束、阻塞、交接 | 当前摘要、证据缺口、下一步；需要时归档 |

围绕一个有意义的增量合并核对。没有相关变化就不更新，也不为检查通过而写无意义改动。已说明无需更新的判断只在同一 scope、同一基线比较依据及相关规则/输入/文档未变化时复用。

## 可执行约定

有持续仓库维护需求且没有等效机制时，由 agent 在实施前建立一份小型机器规则，默认 `devco-repository.json`，也可用项目既有位置并传 `--policy`。它只放检查所需的路径关系，项目入口链接到它，不复制需求和任务列表。

下面是形状示例，路径、必需资料和更新义务必须按当前项目选择，不整套复制成通用目录树：

```json
{
  "schema": 1,
  "paths": {
    "src/": "产品实现",
    "tests/": "相关行为验证",
    "docs/": "当前记录与契约",
    "README.md": "安装、使用和验证",
    "AGENTS.md": "项目协作入口",
    "devco-repository.json": "当前增量的仓库维护规则",
    ".gitignore": "生成物排除"
  },
  "required": ["README.md", "docs/CURRENT.md"],
  "links": ["README.md", "docs/CURRENT.md"],
  "updates": [
    {"id": "public-api", "inputs": ["src/api/"], "documents": ["docs/api.md"]}
  ],
  "ignore": ["runtime/"]
}
```

- 路径相对项目根。尾随 `/` 表示目录及其后代，否则精确匹配文件；不使用 glob。`paths` 给新增文件提供归属，必要的新依赖声明/配置文件也按职责补入；无需逐个登记源码文件。
- `required` 是本增量完成时必须存在的入口，按需选，不要求旧项目补齐通用模板。`links` 只列相关权威入口/资料，自动检查这些文件的相对 Markdown 文件链接（含引用式定义），跳过代码示例、网址、站点根路径和页内锚点；不检查锚点存在性、完整 Markdown 方言或未声明资料。
- `updates` 只声明值得强制核对的输入→文档关系。输入内容、新增/删除或该条规则定义变化时，相关文档须相对基线有内容变化，或记录明确的无需更新理由。只改目录职责说明不触发无关规则；新增/更换关联文档而旧基线没有它的摘要时，不能推断已经更新，须明确 review。语义准确性仍由 agent 对照需求判断；改了几个字不证明文档正确。
- 接入前列出的旧文件不因不符合新布局而失败；旧断链记录为已知遗留，后续新断链（含移动目标导致旧入口断链）失败。已声明的必需入口及更新文档缺失仍失败。并行出现的无关文件先核对归属，不擅自移动/删除或归责。
- 文件清单排除常见工具缓存和显式 `ignore`，Git 仓库还沿用 Git ignore。规则文件应纳入项目版本管理；基线、核对理由和运行证据位于本地 `.project-workflow/`，按项目惯例忽略。检查只枚举文件名，内容读取限于声明的输入和资料，不扫描整个老项目源码或运行产物。

```sh
# 实施前接入一次；保留已有未提交工作作为基线，不提交或覆盖产品文件。
DEVCO_SCOPE="quote-v2" # 示例：沿用当前任务记录中有意义的工作线/增量标识。
python3 "$SKILL_ROOT/scripts/repository_check.py" adopt --root "$PROJECT_ROOT" --scope "$DEVCO_SCOPE"

# 在增量出口或结构变化后核对；默认只输出简短结果，诊断需要时加 --json。
python3 "$SKILL_ROOT/scripts/repository_check.py" check --root "$PROJECT_ROOT" --scope "$DEVCO_SCOPE"

# 确认某条变化不影响文档时记录具体理由；不要把空话或候选猜测当作核对。
python3 "$SKILL_ROOT/scripts/repository_check.py" review --root "$PROJECT_ROOT" \
  --scope "$DEVCO_SCOPE" \
  --rule public-api --reason "仅调整内部缓存；请求、响应和调用方式保持原契约。"

# 增量完成后推进基线；存在检查失败时拒绝推进。
python3 "$SKILL_ROOT/scripts/repository_check.py" checkpoint --root "$PROJECT_ROOT" --scope "$DEVCO_SCOPE"
```

`adopt` 拒绝覆盖既有基线；不删除/重建基线来掩盖本轮问题。首次忘记在修改前接入时，不能把当前所有变更冒充已受检查：优先用已有 Git/任务证据人工核对当前增量，再明确从下一增量接入。`checkpoint` 只确认仓库约定，不替代功能验收；不在每次编辑后调用。未变化时不重复写核对理由。

脚本退出码：`check/checkpoint` 的 0 是声明范围内通过，1 是未通过，2 是配置/执行错误；`adopt/review` 的 0 只说明记录动作成功。脚本不会修复、迁移、归档或删除用户文件，规则与基线也不是防篡改权限系统。

## 基线来源与换增量

一个工作树只有一个活动基线。schema 2 绑定项目根、规则路径、scope 和 Git 分支/提交来源，并保存规则与输入/文档摘要。scope 由 agent 从当前任务记录传入，表示有意义的开发工作线，不是路径过滤器；实际文件范围由规则决定。同任务中的小修、补资料和普通提交继续使用原 scope，不按每轮对话重新 adopt。

同分支普通提交可以继续，但基线提交必须仍是当前 HEAD 的祖先。分支切换、改写/回退导致来源不再延续、Git 与非 Git 状态改变或 scope 不符均报错。空 Git 仓库到同分支首个提交可以继续。规则改变后仍以旧快照核对，`policy_changed` 只报告变化，不自动接纳现状或重建基线。

不同工作线优先使用已有独立 checkout/worktree。确需同根换 scope 时，按以下顺序退出再接入：

1. 按原任务既定方式完成功能或人工验收，再用原 scope 执行 `checkpoint`，确认成功。
2. 建立一个尚不存在的归档目录，例如 `.project-workflow/archive/quote-v1/`；将 `repository-baseline.json` 和存在的 `repository-reviews.json` 从 `.project-workflow/` 移入该目录，保留记录且让活动文件位置空出。不覆盖已有归档，不删除产品文件。
3. 更新原当前记录中的 scope；使用通用计划时同步 `verification.repository_scope`。
4. 在新增量修改前，以新 scope 执行 `adopt`。归档只供追溯，不自动恢复为当前通过依据。

schema 1 没有来源信息，脚本明确拒绝静默升级。保留旧文件，结合原任务/Git 证据人工核对当前增量；在下一明确起点按上面的归档退出步骤接入 schema 2。人工验收项目不必为此编造自动检查。

## 接到完成出口，避免重复工作

已有原生验证器时，将带当前 `--scope` 的 `check` 接入本增量对应的阶段出口。采用本技能通用记录时，在 `verification` 中设置 `repository_policy` 为规则文件相对路径，并设置同一 `repository_scope`，`gate` 会即时执行仓库增量检查；这样即使功能测试证据可复用，声明输入之外的新文件也不会漏检。它不要求改用通用 CURRENT 格式，独立命令可供原生验证器调用。CI 的检出来源和基线取得方式需单独验证，不能把本地结果等同于已接入 CI。

功能测试在有意义的出口用 `verify --reuse`。普通资料待补不阻止功能检查；证据有效时仍复用，最终 `ready` 等待仓库条件也满足。只补不影响检查输入的资料不会重复跑测试。配置或基线来源不合法则在执行前失败。仓库检查无需再作为同一计划中的一条重复命令。完成核对、功能验收和必要记录更新后再 `checkpoint`。

| 时机 | 工作 |
| --- | --- |
| 初次持续实施 | 读相关入口，确定归属与更新关系；需要时接入基线一次 |
| 同一上下文内继续 | 沿用已读规则和有效证据，不重读整库、不重做立项 |
| 新增职责、接口/路径/目标发生相关变化 | 更新受影响的约定和资料，不重新初始化 |
| 增量验收或交接 | 一次相关核对，复用有效测试，更新当前入口 |
| 新会话或上下文丢失 | 恢复短入口，再按当前任务补读 |

Hook 默认只生成 SessionStart 恢复入口；不在每次工具调用/回复结束时全库扫描或驱动续跑。可选的结束提醒与精确工具保护见[辅助脚本说明](helpers-and-hooks.md)。机械检查发现问题才展开对应证据，任务要求或风险确有需要才调用额外专项，不固定每轮组建评审或重复访谈。
