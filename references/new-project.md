# 新项目：确定问题与第一版

**按需读取：** 新项目或重大改向的用途、范围仍不清时使用。先找一个最影响方向的未知，形成当前判断和下一步；不因读到本文件就展开全部阶段。讨论不启动实施，明确局部改动不重新立项。

章节导航：`定义问题` → `按当前未知选方法` → `比较路线与证据` → `第一版可以开始实施的条件`。只读当前决策需要的章节；进入正式实施前核对最后一节的适用条件。

## 定义问题

区分用户希望得到的**结果**、实际使用的**产品**和实现它的**技术机制**，不要把辅助开发的 AI 工具擅自变成产品功能。明确具体使用者、触发场景、现有做法、不解决的后果、为什么现在做，以及最小值得使用的结果。用户缺少领域知识时，先提出有依据的工作定义。

按项目意图选择证据：

- 个人/学习/创作：自用效果、学习或体验；不强加市场验证。
- 内部工具：实际操作者、支持者、流程代价和采用障碍。
- 开源：使用者、维护者、生态适配和持续维护。
- 商业产品：使用者、购买者、预算、购买触发与付费结果。

记录当前判断、可信程度，以及哪条假设不成立会使项目失去价值。分清事实、推断、假设和决定；沿用项目现有记录，避免另建同义文档。

## 按当前未知选方法

| 眼下缺少的证据或决定 | 读取条件与下一步 |
| --- | --- |
| 外部事实、数据可得性、需求或替代方案 | 缺口会改变方向时读 [research-and-positioning.md](research-and-positioning.md)；保留来源、日期、反例和仍待验证的假设。已有充分证据时跳过。 |
| 产品形态、领域/数据模型、系统边界或技术选型 | 需要做具体取舍时读 [architecture-and-risk.md](architecture-and-risk.md)；根据实际约束给推荐，关键选择随原型证据复核。 |
| 新交互产品的核心旅程、状态或技术可行性 | 开始相应原型时读 [prototyping.md](prototyping.md)；选择能回答当前问题的最低成本载体，已有可用设计/试验先复用。 |
| 第一版已具备实施条件 | 进入实施或交付时读 [delivery-and-release.md](delivery-and-release.md) 的适用章节，不提前加载发布流程。 |

链接用于当前缺口，不是读完本文件后的待办清单。只为下一项决策补证据；安全、可逆且在授权内的调研或试验可以继续，不能把尚未决定的产品方向当作已批准需求。

## 比较路线与证据

关键选择存在实质不同路线时，先准确表述用户提议与最强支持证据，再提出可信失败情形。比较最小可用路线、推荐路线和有意义的替代路线；现有服务、手工流程或维持现状也可作为选项。通过效果、时间、成本、维护和撤回难度解释推荐，记录什么证据会改变它；已接受的取舍不重复审批。

按项目实际情况检查使用价值、分发/访问、数据、上游依赖、运营成本、维护和恢复。商业项目再考虑购买与预算；订阅、付费获客、服务软件化才分别检查留存、获客经济性和可标准化程度。内部/开源项目关注采用阻力、支持者或维护者持续性，不机械套商业问题。

把最大风险变成可证伪的小试验，写清可观察阈值与停止/改向条件。桌面研究不足以证明真实使用或需求；商业前提的试验应能否定该前提。只让用户决定会实质改变产品、成本、权限或不可逆取舍的未决问题，给出推荐并保留分歧。

## 第一版可以开始实施的条件

沿用已有目标、约束、授权与证据，不建立新的审批点。正式实施前，核对本轮第一版的适用条件：

- 目标使用者、需要和结果具体，相关需求/采用证据符合项目意图。
- 第一版范围、非目标和验收明确：用户可以进入、完成核心任务、从可信的阻塞故障恢复，得到结果或可用导出。
- 产品形态、采用/分发方式与结果相容；商业项目的商业模式相容。
- 关键架构与技术取舍已结合相关原型/试验证据复核，记录边界、约束、替代方案、代价与重议条件，不为假想规模设计。
- 数据访问、隐私、外部 API、平台控制、运行成本和交付路径可信。
- 对新的交互产品，代表性 Figma 界面流程或可运行 mock 演示覆盖完整核心旅程与影响决定的状态；交互本身重要时需要可运行演示，流程图不能代替。已有合适设计可满足此项。
- 重大技术不确定性有成功试验或明确风险决定；有意义的未知有可证伪检查与停止条件。
- 剩余重大取舍已由用户接受；接受可来自本轮或先前仍适用的明确决定。

不适用或已有证据满足的条件不重复工作。缺口存在时，解决最小未决问题并更新当前记录，不让整个未来产品的设计阻塞一个已明确的第一版。
