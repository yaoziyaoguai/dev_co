# 验证范围与失控恢复

**按需读取：** 检查范围难判断、证据失效或反复失败时使用。明确低影响改动可直接按核心约定验证。

章节导航：缺反馈 → `先形成可验证闭环`；选检查 → `根据影响选择检查`；核对交付 → `验收、实现与证据对应`；界定结论 → `区分完成的不同层次`；失败排查/成本边界 → `反复失败时恢复`。实际执行检查时遵守项目要求和当前授权。

## 先形成可验证闭环

在授权范围内自主推进的前提，是关键上下文足够、操作可执行且影响可控、结果有可观察反馈，以及完成与停止条件清楚。不要求掌握所有信息；明确哪些未知会影响判断，哪些仍可留待后续。已有真实反馈可直接使用，不先填一套就绪问卷。

反馈缺失时，先补最小复现、代表性样本、基线或单条真实路径。预期应来自已确认行为、契约、可信样例或外部证据；用实现本身推导出的断言不能独立证明需求正确。发现验收不合理时提出有依据的修订，不能为取得绿色结果静默降低标准、替换失败样本或伪造真实服务成功。

每轮据反馈保留有证据的改进，再核对约定结果。达到验收即结束当前增量；只有任务确需量化优化时才进入有指标、预算和停止条件的实验。需求价值、真实用户偏好或生产效果缺少证据时保持未确认，不能拿本地测试填补。

## 根据影响选择检查

| 本轮影响 | 通常足够的起点 | 扩大条件 |
| --- | --- | --- |
| 低影响文本、局部样式 | 查看差异；适用时实际渲染/交互检查 | 布局溢出、关键文案改变业务行为 |
| 界面层级、状态或响应式调整 | 按 [UI 设计与验证](ui-design.md) 查看受影响界面，操作相关任务并检查代表性内容与视口 | 共享组件影响多处、状态恢复或键盘操作出现问题 |
| 单模块逻辑、局部 bug | 复现、相关单元/组件测试、必要的类型/静态检查 | 调用方契约或共享行为改变 |
| 跨模块数据、接口、持久化 | 相关测试 + 契约/集成 + 代表性真实路径 | 关键链路、迁移、权限或多个入口受影响 |
| 发布候选、基础配置或共享依赖改变 | 项目规定检查 + 受影响核心流程 E2E；按影响扩大回归 | 真实部署、安装、真实服务仍需独立证明 |

这张表提供判断起点。项目明确要求的检查继续适用；如果要求本身需要调整，解释成本与遗漏风险，依照现有权限处理，不能静默跳过。普通文本更改不需创造“验证标题存在”之类假测试。

先写“选择这些检查，因为影响 X；未覆盖 Y”。环境阻塞时保留对应未验证状态；mock 通过不能证明真实数据源，日志截断、超时或进程启动不能算成功。局部验证后新改了相关代码，应重跑受影响检查；无新变化不重复已通过的昂贵验证。

长检查日志写入已有日志位置或临时文件，返回命令、真实退出码、结果摘要与相关失败上下文，需要诊断时再读原日志。限制的是展示量，不能用 `head` 等提前终止检查、吞掉管道中的失败状态，或把输出被截断当成检查完成。无需为此安装新 hook 或构建日志平台。

如使用辅助验证脚本，inputs 应覆盖相关源码、测试、测试配置、依赖清单/锁文件、契约和引用的有效规格；仅把规格链接放入 CURRENT 不会自动追踪其正文。脚本不会替 agent 推导依赖图。遗漏输入会产生过强的就绪判断，因此最终报告必须说明真实范围。选择整个小模块目录能覆盖以后新增/删除文件；大仓库不要默认全仓哈希。Git ignore、显式 exclude、真实文件优先及链接覆盖的具体规则见[验证输入的选择](helpers-and-hooks.md#验证输入的选择)。

仓库资料待补与功能验证分别判断：`verify --reuse` 在功能证据仍有效时不重跑，最终 gate 仍须满足已配置的仓库条件；功能失败与资料待补同时存在时，两类原因都要保留。配置/基线来源错误则在检查启动前解决。不要用反复运行测试来代替补资料，也不要把 `reused=true` 当作整个增量通过。

通用辅助脚本的复用粒度是整个当前计划，不是每条 check。A、B 在同一计划时，任一相关输入变化都会执行两项；需要其他粒度时复用项目现有任务系统/CI 能力，不默认建设新缓存。最终集成者核对合并后的源码、配置和依赖对应哪些证据，只补跑受影响验证；各分支分别通过不等于合并结果已经验证。

## 验收、实现与证据对应

复杂或跨模块任务在已有任务表、规格或当前记录中保留可追踪关系：每项重要验收对应哪段实现，由哪条测试、手工步骤或真实结果支持，还有什么缺口。已有需求/任务 ID 就复用；小任务用几行说明即可，不强制新增编号、schema 或文档。

交付前从验收回看当前实现，检查遗漏、部分实现、与要求矛盾及范围外扩展。再看声明的检查是否真的覆盖这些行为：所有配置检查通过，也可能漏掉一项需求。脚本 gate 检查证据匹配，不替 agent 做语义覆盖判断。

需求或契约改变时定位受影响的实现、任务与证据；更新权威要求，重跑受影响检查，保留仍适用的结果。测试失效、环境不可用或必须依赖外部验收时，明确该项未验证。若项目采用 Spec Kit，就在其产物中维护关联，当前记录只链接它们。

## 区分完成的不同层次

“本地行为已验证”“真实服务检查通过”“已部署并检查目标版本”“用户认可实际效果”分别记录。哪些层次是本轮验收要求由当前任务决定；原型/离线本轮完成后可以交付，并明确剩余真实验证，不能宣称最终上线完成。

对算法、AI 输出、金融计算或设计质量，挑少量有区分度的普通、边界和失败样本，约定可观察标准。确定性测试之外保留必要人工判断。避免用截图数量、测试数量、代码量或覆盖率百分比代替效果。

## 反复失败时恢复

1. 停止没有新增信息的重复动作，保存日志、最小复现、相关版本和当前未提交工作。
2. 定位是目标漂移、实现错误、数据/环境问题还是上游限制。对下一次尝试写下待证伪的假设和最便宜的区分性检查。
3. 使用已知成功样本/版本对比。只回退本任务明确拥有且可安全撤回的改动，不重置用户工作，不用替换整套技术绕过尚未诊断的问题。
4. 修正本轮计划与记忆。把未决定的新方向记为候选，实际阻塞写明需要的输入；不要把失败隐藏为“已完成”或无限继续。

有外部请求、付费或批量成本时，记录用户认可的范围/预算，先跑代表性样本。到达界限停止受影响操作。普通脚本与 prompt 无法统计所有调用或拦截所有工具；真正的硬上限应配置在服务商、宿主权限或受控执行入口，不能由本技能虚假承诺。
