# 按当前问题选择专项技能

**按需读取：** dev_co 已适用于本轮任务，而且需要某项专项能力时，查对应行。这里列的是可选能力，不是每轮开发的流程清单，也不是安装清单。独立分析、单次审查和孤立小修改仍按主入口判断，不因涉及某个技术栈而进入 dev_co。

先用当前需求和证据判断缺什么，再从宿主技能目录确认可用入口。用户已指定的方法优先；有多项候选时先选最贴合当前问题的一项，出现不同的必要问题再补充。没有相应技能就使用现有工具和项目约定；只有缺失能力确实阻塞任务时才说明，不自动安装技能、插件或依赖。

## 可用性与选择顺序

技能名称按宿主目录解析，可能有命名空间或前缀；表中名称是能力入口，不是固定安装路径。区分三件事：磁盘有文件、当前宿主能加载、依赖工具可执行。先查会话技能目录或宿主支持的发现方式；未列出时，仅在宿主允许且路径可核实时读本地入口，不把磁盘存在当成工具已可用。不要搜索凭据或自动安装来补齐能力。

先沿用用户已选方法，再按当前缺口选一个首选；同一问题有多种技能时不同时启动多套完整流程。读取入口后核对其实际要求，不能只凭描述判断兼容。若技能默认要求额外提交、部署、付费、外发内容或无上限实验，按当前授权缩小；无法兼容就使用现有工具完成有界任务，并说明限制。

## 工程与验证

| 当前问题 | 可用时选用 | 选择边界 |
| --- | --- | --- |
| 领域对象、状态或术语不清，影响接口或实现 | `domain-modeling` | 单纯读取 `GLOSSARY.md` 或已有术语文档不启动技能；需要挑战术语、修改模型或记录领域决定时才加载。复用已有领域文档，只处理当前分歧；不因技能模板要求而迁移或清空现有 `CONTEXT.md` |
| 前后端或服务之间的共享 API、事件结构要改变 | `contract-first` | 处理受影响契约和调用方；局部实现不启动跨模块契约流程 |
| bug 的原因未明、失败反复出现 | `diagnosing-bugs` | 先取得可复现反馈并检验假设；原因与改法已明确时直接修复并验证 |
| 行为明确且测试能暴露回归；或需要检验大量输入的性质 | `tdd`；往返、幂等、不变量、解析边界用 `property-based-testing` | 按行为选测试方法，不叠加两个完整流程，不为简单修改引入测试框架 |
| 查询、抽取、join、去重、时间口径或数据变换的结果正确性需要检查 | `sql-data-review` | 聚焦数据语义、基数、隐私与验证查询；引擎、索引与事务问题选 `mysql`。不自动连接生产环境或执行写入；普通 SQL 解释不启动完整数据治理流程 |
| 已发生 merge/rebase 冲突，需要保留双方变更意图 | 先用现有 Git 工具；本地仍有兼容的 `resolving-merge-conflicts` 时可按需参考 | 上游已移除该技能，不作为必要依赖。核对冲突、原始意图和相关验证；暂存、提交、continue 或 abort 按当前授权及状态判断，不暂存无关文件，不为完成流程强行选择行为 |
| 本轮实际修改 Rust，或设计/排查 MySQL | `rust-best-practices` / `mysql` | 沿用项目版本、features、数据库引擎和已授权连接；只读代码/SQL建议无需连接数据库 |
| React 组件 API、变体或共享状态难以维护 | `vercel-composition-patterns` | 只改受影响的组件边界；普通 JSX/样式变化不自动重构组件架构 |
| React 请求、渲染、加载、缓存或 bundle 存在具体性能问题 | `vercel-react-best-practices` | 按实际框架与 SSR/CSR 选规则，用测量验证有成本的优化 |
| 模块边界或结构取舍需要改善 | 局部判断参考 `codebase-design`；用户明确选用架构探索工作流时用 `improve-codebase-architecture` | 后者保留显式调用策略，不把有界 bug 修复扩大为全仓重构 |

代码审查按本次风险使用宿主工具或独立审查角色。保留发现、依据和验证结果即可；有角色不意味着每次都组建审查团队，也不自动加载另一套开发或发布总流程。

## 性能问题先分流

| 当前问题 | 首选 | 选择边界 |
| --- | --- | --- |
| 原因未明，不知道慢在哪里 | `diagnosing-bugs` | 先取得可复现反馈与瓶颈证据；已知改法直接修复 |
| 已定位 React / Next.js 请求、渲染、加载或 bundle 问题 | `vercel-react-best-practices` | 使用实际框架规则与测量，不扩成全站优化 |
| 已有可重复测量，需要比较多个改法 | `ce-optimize` | 先约定指标、实验范围、预算和停止条件；已知修法、一次测速和结果分析不启动多轮实验 |
| 需要网页性能基线或退化检测 | `benchmark` | 测量与回归检测不自动授权修复、提交或部署 |
| 用户明确选用“打开到能用”的专项提速流程 | `huashu-flash` | 加载前确认当前版本可遵守既定目标、停止条件和提交授权；不沿用默认翻倍目标或达标后无限继续。尚有冲突时用现有测量工具完成本轮范围 |

只保留一套实验管理和一份当前目标；性能报告、配对测量和实验日志作为专项证据链接回来。

## 安全问题先分流

普通开发按相关风险做局部安全检查；用户要求专项安全工作，或已有具体漏洞需要处理时，再选相应能力。下表使用 Codex Security 的能力名称；宿主只有 `cso` 等替代入口时先核对范围，选择一套可用流程，不叠加完整扫描。

| 当前问题 | 可用时选用 | 选择边界 |
| --- | --- | --- |
| 审查 PR、提交、分支或工作区差异的安全风险 | `codex-security:security-diff-scan` | 范围跟随差异，不自动变为全仓审计 |
| 用户要求仓库或指定目录安全审计 | `codex-security:security-scan` | 深度、多轮审计仅在明确需要时选 `deep-security-scan`；普通鉴权修改不默认触发 |
| 已给出安全发现，需要核实 | `codex-security:triage-finding` 或 `validation` | 按来源和阶段选一个入口，不把一般正确性问题改称漏洞 |
| 用户明确要求修复已知或合理可信的漏洞 | `codex-security:fix-finding` | 修复与本轮必要验证保持闭环；独立 `verify-fix` 仅在明确要求时调用 |
| 用户要求威胁模型、安全策略或结构性加固方案 | 对应 `threat-model`、`define-security-policy` 或 `propose-security-hardening` | 不因经过安全扫描就自动新增这些交付物，不自动外发发现或创建工单 |

## 理解代码、研究与文档

| 当前问题 | 可用时选用 | 选择边界 |
| --- | --- | --- |
| 已有知识图谱可帮助定位模块、关系或变更影响 | `understand-chat` / `understand-diff` | 先确认图谱对应的代码版本；源码仍是实现依据。局部搜索足够时直接搜索，不重建全仓图谱 |
| 确需生成架构图谱或接手导航 | `understand`；已有 graphify 产物且适配任务时可沿用对应入口 | 生成前限定范围、成本和产物位置，确认是否写配置或启用自动更新；不同时维护两套图谱，不把全部代码问答变成图谱构建 |
| 开发决策需要有出处的技术比较或事实核查 | `research-evidence` | 普通 API 查询使用官方资料和现有工具；独立研究不因此进入 dev_co，不默认把私有材料发给外部服务 |
| 功能改变后使用方式、配置或接口文档需要同步 | 小变化直接编辑；缺整类文档时选 `document-generate`；发布文档核对选 `document-release` | 只维护受影响文档；不因为改一个参数就审计全套文档，也不以文档流程替代真实验证 |

## 界面设计与实际验证

先沿用 [ui-design.md](ui-design.md) 中的项目任务、设计约定和状态要求，再按当前缺口选用：

| 当前缺口 | 可用时选用 | 与当前工作的关系 |
| --- | --- | --- |
| 信息层级、视觉方向或整体界面质量需要设计与迭代 | `oil-ui` | 接手当前设计问题；已有需求和方向继续有效，不重复访谈或全站改版 |
| 需要具体配色、字体、交互、图表或平台规范参考 | `ui-ux-pro-max` | 查询当前问题所需的本地资料，供现有设计取舍使用；不自动生成另一套设计系统 |
| 需要选择、接入或适配 UI 组件来源 | `compose-ui-kit`；已有或明确要求引入 shadcn 时用 `shadcn` | 前者负责选型与整合，后者处理具体组件约定；不因 React 项目而安装组件库 |
| 要核对受影响 UI 的可访问性、表单、导航或反馈 | `web-design-guidelines` | 保持当前检查范围；明确的一处对比度或间距问题无需完整视觉设计流程 |
| 从 Figma 实施、回写设计、维护组件映射或规格 | 宿主对应的 `figma:*` 技能 | 按方向选择 design-to-code、生成设计、Code Connect 或 spec 入口；使用工具前加载其必需前置技能。保留已定设计，不自动创建外部文件或重新访谈 |
| 需要实际页面、截图、控制台或交互证据 | 宿主现有浏览器工具；终端自动化适用时用 `playwright` | 选择能访问目标环境的工具并查看实际结果；源码检查、视觉检查、交互与真实集成分别报告 |

`design-taste-frontend` 沿用用户的显式选用策略，需要时先确认该宿主入口可用。一般 UI 请求不自动转交它。`lfg`、`review`、`qa` 也保持主入口的显式调用约定。

## 显式选择与任务出口

尊重各技能现有的显式调用策略；被本表提到不构成用户选择。`lfg`、`review`、`qa`、`code-review`、`improve-codebase-architecture`、`prototype`、`handoff`、`matt-retro`、`writing-for-agents`、`design-taste-frontend` 不由普通开发请求自动启动。`autoplan`、`plan-*-review`、`office-hours` 等完整规划流程也只在用户选用时接入，避免替换当前主流程。

- 要把方案发布为任务时，才按用户选择使用 `to-prd`、`to-issues` 或 `request-refactor-plan`；只整理方案不授权写外部任务系统。
- 明确需要配置工程环境时，才选择 `setup-pre-commit`、`setup-deploy`、`setup-gbrain` 或 Git guardrails 等入口；安装 dev_co 不启用它们。
- `ship`、`land-and-deploy`、`publish-site-article` 按本轮交付请求及授权使用，技能名称不授予提交、推送、部署或公开发布权限。
- HTML 解释、图片、视频、文档、表格、演示、PDF 和文字润色，按交付物选择对应技能；只有本轮确需该产物才加载，不能替代实现或验证。独立制作这些产物不进入开发流程。
- 独立评测可按请求选 `agent-eval`，仍不进入 dev_co；开发评测系统时，专项评测是当前开发增量的证据。

## 专项结果回到当前开发

专项任务只接收本轮相关目标、边界、代码和证据，不复制整段会话或重新建立项目总计划。已有决定和授权继续有效；遇到新的实质取舍、成本或权限才提出。子代理沿用用户选择的模型与宿主规则，专项技能不能借自己的默认值扩大调用范围。

把结果、必要变更、验证与剩余缺口写回原项目记录或交付说明。优化 spec、实验日志、截图等可以作为链接证据保留；它们不替代项目当前目标。阶段完成后回到已约定的开发增量，新增机会保留为候选，不自动开始下一项优化。
