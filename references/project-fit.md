# 让取舍贴合项目

**按需读取：** 已有项目背景不足以指导当前设计、实施或验收，或方案明显在套用通用模板时使用。明确的局部改动直接沿用已有判断；不新增固定的“项目画像”阶段、问卷、配置文件或审批点。

章节导航：找依据 → `从项目事实到本轮取舍`；决定投入 → `按阶段与约束推进`；混合产品或多个角色 → `以当前任务为单位`。新项目用途仍不清时用 [new-project.md](new-project.md)，不是在这里猜定产品方向。

## 从项目事实到本轮取舍

从当前请求、项目记录、代表性流程与相关代码找依据。只补会改变本轮选择的缺口，不为填写模板扩大搜索。分清：

- **谁在什么情境下使用：** 实际操作者、使用频率、设备、时间压力或环境限制；购买者、维护者与操作者的需要可能不同。
- **项目主体是什么：** 用户真正查看、处理或产出的领域对象及其关系，例如照片与组图、订单与履约、账单与金额。技术栈和“AI 产品”标签不能替代这个定义。
- **什么结果有价值：** 从触发到结果的主要任务，以及出错时必须保留的信息和恢复方式。
- **现有基础是什么：** 当前阶段、有效接口、数据约定、设计语言、可用集成和交付条件；从代码及证据核实，不凭文件名或项目自称“成熟”推断。

把影响当前决定的事实连成“依据 → 取舍 → 验证”的短说明，沿用现有记录。已清楚的内容直接用于工作，无须每轮重复输出或让用户重新确认。

例如同样要求“更好用”：

| 已知项目事实 | 对本轮选择的影响 | 合适的验证 |
| --- | --- | --- |
| 编辑每天比较多条待发布内容 | 保留状态、必要字段与批量处理的连续性，优先解决定位和恢复问题 | 用真实密度完成查找、修改及错误恢复；有时效目标时再测时间 |
| 读者来浏览摄影组图 | 让作品、组图关系和阅读顺序成为界面重点，按浏览任务安排操作 | 从入口找到目标组图，图片加载异常时仍理解内容与下一步 |
| 财务通过既有 CLI 处理账单 | 围绕文件契约、金额正确性、兼容调用和可定位错误交付增量 | 使用代表性文件检查金额、输出与退出码，同时保留旧调用行为 |

这些是推导示例，不是按行业套用的功能包。用户未要求的批量操作、账户、同步、商业化或新界面不因此进入范围。

## 按阶段与约束推进

- **方向尚未明确：** 找会改变决定的未知，复用已有证据；需要时用最小代表性试验。不能以“先搭基础”为由提前做完整系统。
- **首个可用版本：** 先让项目的核心对象走完一条有价值的任务链，覆盖可信的阻塞故障；不机械搭齐登录、仪表盘、管理后台等通用模块。
- **已有产品的增量：** 明确本轮改变什么、哪些旧行为必须兼容，复用有效组件与技术选择；既有设计若妨碍本轮任务，提出有依据的局部调整，不把继承偶然缺陷当成一致性。

技术取舍由真实数据量、离线与隐私需要、外部依赖和维护能力约束，具体比较使用 [architecture-and-risk.md](architecture-and-risk.md)。项目标签不自动授予更高复杂度；小改也不能因“自用”而省略金额、数据完整性或破坏性操作的必要验证。

## 以当前任务为单位

同一项目的公开介绍页、用户工作区和管理界面可以有不同的信息重点，遵守共同品牌与数据语义即可。混合产品按当前角色和任务选择布局与检查，不给整个项目强行套一个风格或流程。

实现前用代表性内容核对主要对象、关系与动作是否进入方案；交付前回到同一个任务检验结果。复用通用组件没有问题，只有换了项目名和颜色、却未考虑关键内容或操作差异的方案需要重审。

会影响后续工作的判断写回原有当前记录或设计约定，优先引用既有来源；尚未采纳的方向保持候选。讨论阶段仅给判断，不据此改写项目事实或创建第二份计划。
